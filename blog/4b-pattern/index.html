A combinatorial bandit is a wrapper, not an algorithm

Posts 1–4 looked like four different problems with four different solutions. They were the same algorithm four times. Here is the wrapper that proves it — change one function call, learn a different classical algorithm's parameters.

The reduction

This is the entire combinatorial-bandit pattern. The only line that changes between Posts 1–4 is the one marked.

↓ swap this line 
# one scalar estimate per parameter (edge / pair / arm)
est = Estimates()
for t in range(T):
    optimistic = est.mean − bonus(est.count, t)   # UCB optimism
    action     = solver(problem, optimistic)    # ← the classical algorithm
    observed   = problem.play(action)             # semi-bandit feedback
    est.update(observed)                          # only touched params

Set solver = argmax and you have Post 1's multi-armed bandit. Set solver = Dijkstra and you have Post 3. Set solver = 2opt and you have Post 4. The learning machinery — optimistic estimates, semi-bandit updates, the regret it incurs — is byte-for-byte identical.

Act 1 — Why they're the same

Each of the first four posts had a classical algorithm that solves the problem when the parameters are known: scan-for-max, sort, Dijkstra, Christofides/2-opt. The "unknown parameters" version doesn't replace that algorithm. It wraps it: run the classical solver on your current best (optimistic) guess of the parameters, take the action it returns, observe the parameters you touched, update your guess, repeat.

The optimism — subtracting a confidence bonus so under-sampled parameters look attractively cheap — is what makes the wrapper explore. The classical solver is what makes it exploit structure. Neither half is new; the combination is the combinatorial bandit.

Three classical algorithms, written decades apart for fully-specified inputs, all learning their hidden inputs through one loop you never edited. That is the content of "combinatorial bandits work on top of other algorithms": they are a generic adapter that turns any known-parameter solver into an unknown-parameter learner, provided the feedback decomposes per component (semi-bandit) so estimates are shared across actions.

Act 3 — Bradley-Terry is the same trick for ranking

Post 2 (sorting with noisy comparisons) is this wrapper too — the base "solver" is a ranking aggregator, and the parameters are Bradley-Terry skills. The Bradley-Terry model says a comparison goes P(i ≻ j) = σ(s_i − s_j) for latent skills s. Each comparison you run is a noisy observation of one skill difference; fit the skills by maximum likelihood; sort by fitted skill. The combinatorial bandit's job is the experimental design — which pairs to compare next so the skill estimates converge fastest. (Post 2 now shows that fit converging live.)

So the menu of "solvers" the wrapper accepts is broad: argmax, sort/rank-aggregate, Dijkstra, Prim, 2-opt, and — the reason this series exists — the greedy submodular page composer of the research project. Running the wrapper on that solver is exactly what the paper calls GreedyLinTS (paper §5.4c): a combinatorial bandit on top of the EDP page-composition algorithm.

Where this points

If a combinatorial bandit is "optimism + a classical solver," then EDP is "a prior + the same classical solver." Instead of an optimism term that explores from scratch, the LLM writes down a starting guess of the parameters that is already good — and a small online correction (the SGD in Bayesian-EDP) plays the role the optimism term used to play. Same wrapper shape; the exploration budget is replaced by world knowledge.

That is the move Posts 5 and 6 make concrete. The combinatorial bandit learns the parameters from clicks; EDP starts most of the way there because someone who understood the problem wrote them down first.
