Human-like priors as executable policy

Posts 1–4 learned by exploring; Post 5 learned by reasoning from world knowledge. EDP fuses them: the LLM authors a readable model from what it knows, the solver runs on it from session zero, and data calibrates the same named parameters — world knowledge for the cold-start, exploration for the rest.

Live: an actual EDP instance from the research project · 245 named parameters, authored offline from shopping psychology, zero training data. Drag the sliders — watch hidden intent estimates change, then watch the solver compose a page.

The previous level put a Gym around classical problems: sorting has hidden skill values, shortest path has hidden edge weights, TSP has hidden distances. A bandit estimates those parameters from trials. An LLM can also guess, but score-only OPRO is a thin feedback channel. EDP asks for a better interface: make the hidden-parameter estimator itself a readable artifact.

That idea is not WPO-specific. For sorting, a named GAM might estimate item skill from signals such as reviews, price, or model-written difficulty notes. For routing, it might estimate congestion from weather, time, and events. For TSP, it might estimate distance penalties from traffic or risk. The solver can still be sort, Dijkstra, or 2-opt; the EDP is the human-readable prior over the parameters those solvers need.

Act 1 — The general shape

An EDP has three pieces. First, a Gym-like environment defines what can be observed and how reward appears. Second, named GAM curves turn observable signals into latent parameter estimates: congestion, uncertainty, fit anxiety, comparison friction, or whatever the problem needs. Third, a classical solver acts on those estimates. The representation is small enough for an LLM to author, and explicit enough for a human to review.

EDP / GAM object
Signals:x = observed features (clicks, price dwell, weather, review scores …)
Latent intensities:zp = Σj wpj · gpj(xj)   — gpj named piecewise-linear curves
Module score:s(m) = basem + Σp on_remm,p·remainingp + Σp on_covm,p·coveragep − decaym·slot
Solver (greedy):at each slot pick argmaxm s(m); update remaining/coverage; repeat ×6
Edit unit:one named scalar, e.g. size_guide.on_rem.F32 ← 2.4, with a reason

Why a GAM: the policy is a sum of named contributions, so every decision factors into readable terms and every parameter has an address an LLM can name and a human can plot. That is what makes it editable by both — the property a neural net's weights[847][22] does not have.

The fusion (from Post 5): the LLM authors {w, g, on_rem, …} from world knowledge — the warm start OPRO gave you — and a regularised-SGD channel nudges those same named scalars from data — the explore-and-correct loop the bandits gave you. θ ← θLLM + SGD-correction.

Act 2 — Why this is different from "ask an LLM"

Two reasons. First, the grammar is small and named, so an LLM can hold the entire policy in one prompt, edit a curve, and have the change be both readable (a human sees what changed) and executable (the system serves the new version with no retraining). Try asking a model to directly choose every route, sort order, or page at runtime; now compare that with asking it to edit fit_reassurance.on_rem.F32 = 2.4 in a 9 KB JSON. The latter is reviewable software.

Second — and this is the load-bearing move — the small named GAM is a fixed compositional structure, not free-form code. Every page decision factors as base + Σ(on_rem · remaining) + Σ(on_cov · coverage) − slot_decay · slot. The LLM doesn't write the algorithm; it writes the numbers. The algorithm runs in microseconds, deterministically, in pure Python or compiled JavaScript.

Three artifacts an LLM might hand you

A trained neural net: not closed under edits

Intuition: powerful, but the policy lives in thousands of anonymous weights. There is no weights[847][22] an LLM can reason about, and no plot a human can audit.

a = fθ(x),  θ ∈ ℝthousands, unnamed
  • Learns from data: yes (gradient).
  • LLM-editable / human-auditable: no.

An OPRO free-form string: editable but ungrounded

Intuition: Post 5's artifact — a candidate the LLM proposes from score history. The model can rewrite it, but there is no fixed structure, no per-parameter meaning, and no gradient channel to calibrate it from data.

xt+1 ~ πLLM(x | scored history)
  • Learns from data: only via score-only re-proposal (weak).
  • LLM-editable: yes; typed / auditable: no.

A named GAM: closed under both LLM and gradient edits

Intuition: ~245 named scalars. Small enough to fit in one prompt, typed enough that every edit is well-formed and plottable, and differentiable so SGD can calibrate the same numbers from data. This is the EDP fit — and why it sits between the other two.

θ = {wpj, gpj, basem, on_remm,p, …},  ~245 named scalars
θ ← θLLM-authored  then  θ ← θ − η ∇θ regret (regularised)
  • Learns from data: yes (SGD on named params).
  • LLM-editable + human-auditable: yes. Closure under both.

Act 3 — What this skips, and what it doesn't

Bandits need exploration because their priors are weak. EDP needs less exploration for the things the LLM or human already knows: that fit reassurance addresses size anxiety, that a snowstorm changes travel time, that a noisy comparison near a decision boundary deserves more samples. These facts are learnable from trials, but expensive to learn from scratch.

What it does not skip: calibration. The LLM said "size_chart at 0.6 means moderate concern" but you may need to nudge it to 0.55. It said "fit_reassurance addresses F3.2 with weight 2.2" but production data might want 2.4. These are small calibrations to the LLM's prior, and they should still come from data.

So you have an LLM-authored, zero-data, sub-millisecond policy that starts with a useful guess. The natural next question is whether it survives production feedback: delayed rewards, noisy measurements, and page-level attribution where the system sees only the total result, not which component deserved credit.
